# Тест-план: TaskManager (gRPC + REST)

## 1. Объект и цели тестирования

Сервис `TaskManager` — CRUD над задачами (in-memory хранилище), доступен
по двум протоколам: gRPC (основной) и REST-шлюз поверх него (FastAPI).

Цель тестирования — убедиться, что:

- бизнес-контракт CRUD соблюдается на обоих протоколах одинаково;
- сервис не теряет и не портит данные при параллельных запросах;
- сервис ведёт себя предсказуемо при таймаутах и отменённых вызовах
  клиента, а не зависает;
- ошибочные и граничные входные данные обрабатываются осознанно, а не
  падают в неопределённое поведение;
- у сервиса есть стандартный способ проверить его живость (health-check)
  для внешних систем (оркестраторы, балансировщики).

Вне зоны ответственности этого тест-плана: производительность под
нагрузкой (нагрузочное тестирование в проект пока не включено),
персистентность данных (хранилище намеренно in-memory).

## 2. Риск-ориентированная стратегия (RBT)

Тестирование строится не "покрыть все методы одинаково", а от рисков:
чем выше цена ошибки, тем больше тестов и внимания.

| Риск | Почему это дорого | Чем закрыт |
|---|---|---|
| Потеря/порча данных при параллельных запросах к одной задаче | Тихая потеря данных — самый дорогой класс багов, пользователь не узнает, что что-то сломалось | [`test_concurrency.py`](../tests/test_concurrency.py) |
| Клиент виснет, если сервер не отвечает | В проде превращается в каскадный отказ (клиенты копят зависшие запросы) | [`test_deadlines.py`](../tests/test_deadlines.py) |
| Молчаливая порча данных на границах ввода (пустые/огромные/юникод строки) | Проявляется случайно, сложно воспроизвести в проде | [`test_boundary_and_known_issues.py`](../tests/test_boundary_and_known_issues.py) |
| Расхождение поведения gRPC и REST-шлюза | REST — внешний фасад; если он врёт про контракт, ломаются все внешние клиенты | [`test_rest_gateway.py`](../tests/test_rest_gateway.py) дублирует сценарии [`test_task_manager.py`](../tests/test_task_manager.py) |
| Оркестратор не может понять, жив ли сервис | Неправильный health-check = трафик идёт на мёртвый под | [`test_health.py`](../tests/test_health.py) |
| Базовый CRUD-контракт нарушен | Это ядро продукта, любая регрессия тут — блокер | [`test_task_manager.py`](../tests/test_task_manager.py) (маркер `smoke`) |

## 3. Тест-уровни (маркеры pytest)

Расшифровка маркеров из `pytest.ini` — что каждый значит и когда каким
пользоваться:

| Маркер | Что проверяет | Когда гонять |
|---|---|---|
| `smoke` | Основной CRUD happy path | Всегда, первым; красный smoke — блокер, дальше можно не запускать |
| `negative` | Ошибочные сценарии (невалидные данные, несуществующий id) | В каждом прогоне CI |
| `boundary` | Граничные значения (BVA) и задокументированные известные ограничения | В каждом прогоне CI |
| `concurrency` | Параллельный доступ, race condition | В каждом прогоне CI; отдельно — при подозрении на гонки после правок в `service.py` |
| без маркера | Health-check, deadline/cancellation, REST-паритет — технические/протокольные проверки | В каждом прогоне CI |

Прогнать один уровень: `pytest -m smoke`.

## 4. Известные ограничения

- `ListTasks` не поддерживает `page_size`/`page_token` — при большом
  количестве задач возвращает всё одним ответом. Контракт API это не
  нарушает, но для прод-масштаба — риск (объём ответа, память).
  Зафиксировано тестом
  [`test_list_tasks_has_no_pagination_known_limitation`](../tests/test_boundary_and_known_issues.py),
  не исправлено намеренно — не в рамках текущего объёма проекта.
- Title из одних пробелов проходит валидацию (`if not request.title`
  отклоняет только буквально пустую строку) — осознанная граница
  текущей реализации, см.
  [`test_create_task_title_of_only_whitespace_is_accepted`](../tests/test_boundary_and_known_issues.py).

## 5. Критерии готовности (Definition of Done для PR)

- CI зелёный (lint, format-check, весь тест-сьют, сборка Docker-образа).
- `ruff check .` и `black --check .` без замечаний.
- Новый RPC-метод или REST-эндпоинт покрыт минимум happy path +
  negative-сценарием (см. чек-лист ниже).
- Покрытие бизнес-логики (`service.py`, `rest_gateway.py`) не падает
  ниже уже достигнутого уровня — см. `htmlcov/index.html` после
  `pytest`.

## 6. Чек-лист: добавляем новый RPC-метод / REST-эндпоинт

- [ ] Happy path протестирован (`smoke`)
- [ ] Хотя бы один negative-сценарий (`negative`)
- [ ] Граничные значения входных данных рассмотрены — если нашлось
      что-то похожее на пункт из раздела 4, задокументировано так же
      явно тестом, а не пропущено молча
- [ ] Если метод меняет общее состояние — учтено, нужен ли тест на
      конкурентный доступ (`concurrency`)
- [ ] Тест размечен `@allure.feature` / `@allure.story` и обёрнут в
      `allure.step`
- [ ] Если метод есть в gRPC — проверено, нужно ли зеркалить его в
      REST-шлюзе (`rest_gateway.py`) и в `test_rest_gateway.py`
- [ ] `README.md` обновлён, если поменялась структура проекта или
      способ запуска
- [ ] `ruff check .` и `black --check .` проходят локально перед пушем
